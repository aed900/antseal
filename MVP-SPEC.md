## Context

Research previously established (external facts re-verified against live sources 2026-07-27):

- Autonomi 2.0 (the WithAutonomi/Saorsa upstream; `maidsafe/autonomi` redirects there) is live since ~April 2026 and usable **today for immutable, pay-once-forever storage** (chunks/files via `ant-core` 0.5.x on crates.io, payments on Arbitrum One). Mutable data types don't exist yet — irrelevant here, since notarization only needs immutability.
- The timestamping market is commoditized (OpenTimestamps is free; WIPO PROOF died of low demand, 2022). The defensible product is the **bundle**: private-until-revealed permanent vault + **granular, provable selective disclosure** + zero-install third-party verification. No product shipping salted Merkle-level partial reveal was found (positioning hypothesis, not a verified fact).
- Two hard design constraints: (1) Autonomi provides no trusted clock — timestamps come from independent anchors (OTS / RFC 3161; the 1.0→2.0 transition was a full data reset, so evidence must survive resets); (2) Autonomi's native self-encryption is convergent — secret work must be wrapped in randomized AEAD before upload or it's vulnerable to confirmation attacks. **Corollary applied throughout: nothing content-derived is ever stored or shipped unsalted — including per-file hashes.**

MVP scope decisions (user-confirmed):

1. **Form factor**: Rust CLI (non-custodial, user's own wallet) + static web verifier page (same core via WASM). No backend.
2. **Reveal depth**: manifests commit the salted fine-grained byte-tree **from day one, for every file — text and binary — sealed with a fine tree (the default)**; MVP reveal tooling is whole-work + per-unit; byte-range reveal commands land in v1.1. Files opted out via `--no-fine-tree` are whole-file-revealable only, permanently, and `seal` says so.
3. **Anchors**: OpenTimestamps (Bitcoin) + ≥2 free RFC 3161 TSAs on every seal (**at least one TSA token must succeed or `seal` aborts**; `--force-degraded` overrides). The Arbitrum payment receipt is **captured in full on every seal but demoted to "supporting evidence" in all MVP verdicts** — no on-chain datum contains `anchor_digest` (defined below); its verification chain is v1.1 (see Anchoring). eIDAS-qualified stamps = later paid tier.
4. **Network**: develop and test on the local devnet and the **self-hosted Arbitrum-Sepolia devnet** (there is no public Autonomi 2.0 testnet today — upstream's `start-devnet-sepolia` example runs 25 local nodes paying the real deployed Arbitrum Sepolia contracts); **release defaults to Arbitrum One mainnet**, `--network arbitrum-sepolia|devnet` as development flags. Maintainer accepts tracking upstream breaking changes (weekly-to-biweekly cadence upstream; pin + adapter layer below; re-verify the pin at M0 start).

## Product definition

**One-liner**: Seal your work into permanent encrypted public storage with independently verifiable timestamps; later, reveal all of it — or any chosen part — to anyone, with proof it belongs to what you sealed.

**MVP user**: technical-ish creators, researchers, inventors, small legal/IP practices comfortable with a CLI. **Counterparties/verifiers need zero install** (drag a proof file onto a web page).

**Positioning constraints**: never call it a "notary" in legal copy — and never claim "priority" unqualified. A seal proves **the holder of key X possessed this content by time T** — not authorship, not exclusive possession; an earlier seal by someone who received your work outranks yours ("**seal before you share**"). Docs must state both limits, plus a compelled-disclosure note: the vault holder can always be forced to reveal; vault destruction is the only, irreversible, opt-out. All verdict copy uses possession language.

**Explicitly OUT of MVP scope**: see the single canonical **Parking lot** section at the end.

## Core user flows

1. **Seal**: `antseal seal <path>… --title "..."`. Normative order puts every cheap, failable step *before* the one irreversible paid one: canonicalize → encrypt units (local; **journaled**) → build + sign manifest → **encrypt the manifest** (`k_m`) → compute all ciphertext addresses (units + encrypted manifest, via `self_encryption`) → `quote_batch` over the full blob set → **permanence consent** (ANT + ETH balances beside the *true, complete* quote; distinct errors for insufficient token vs gas; file list, byte totals, cost, "upload is permanent, public, and irreversible" — interactive confirm, `--yes` for scripts) → **anchor submission with the ≥1-TSA-or-abort gate** (OTS calendar submit → pending; ≥2 TSAs, abort before payment unless ≥1 token returns, `--force-degraded` overrides) → **`pay`** (one Merkle-batch tx; **`PaymentReceipt` captured + journaled the instant it lands**) → **`finalize_batch`** (upload ciphertexts + encrypted manifest; paid, permanent) → print work-id + cost. Anchoring fails cheaply and reversibly (no money spent); only after the anchor gate passes does anything paid or permanent happen, and the receipt is journaled before the upload so a crash never re-pays. Nothing readable ever leaves the machine: the network holds only randomized-AEAD ciphertexts (units *and* manifest). The title *is* embedded in the (plaintext) manifest that every proof bundle carries, and `seal` warns it will be visible to bundle recipients.
2. **Status/upgrade**: `antseal status <work-id> [--upgrade]` → shows each anchor's state; completes pending OTS attestations. Additionally, **every CLI invocation opportunistically attempts pending OTS upgrades**, and `list` nags on works whose only strong anchor is still pending.
3. **Reveal**: `antseal reveal <work-id> (--all | --units 3,5) -o pitch.sealproof` → prints exactly which units (file, byte-range, size, snippet) will be **irreversibly disclosed** and requires confirmation (`--yes` for scripts) → self-contained proof bundle. Fetches ciphertext from Autonomi when no local copy exists. `--include-receipt` opts the Arbitrum receipt into the bundle (off by default — it exposes the paying wallet; see Risks).
4. **Restore**: `antseal restore <work-id> [-o dir]` → fetch ciphertexts via the storage backend, decrypt with vault-derived keys, verify against the manifest commitments (`raw_commit`/`canon_commit`), write the original files. This is the permanent vault's door; the M4 gate includes a clean-machine, vault-backup-only disk-loss recovery drill.
5. **Verify** (third party): drag `pitch.sealproof` onto the static page (or `antseal verify pitch.sealproof`) → offline verdict: what content is proven, its position in the sealed whole (blackout redaction view), and per-anchor status with one headline time (see Verifier page). Optional `--online` confirms the Bitcoin header and the Arbitrum tx via **two pinned, must-agree public endpoints per source** (TSA cert chains are already validated offline against the pinned root store with genTime LTV — see Anchoring — so they need no online step). Optional `--live` (**CLI only** — the page is `antseal-core`-WASM with no network layer and there is no backend; the page's storage story is the offline address-recomputation of the storage-linkage layer) re-fetches ciphertexts from Autonomi and byte-compares them against the bundle to prove persistence.

**Key external dependency**: `ant-core = "=0.5.0"` (pin exactly; pre-1.0, weekly-to-biweekly releases). All **Autonomi storage** network use goes through `antseal-net::StorageBackend` (anchor network I/O — OTS/TSA/Arbitrum — lives in `antseal-anchor`; this is the churn-isolation boundary the risk section needs), shaped **batch-first** to match upstream's payment model:

```
quote_batch(&[Blob])                       -> CostQuote
pay(&CostQuote)                            -> PaymentReceipt   // one Merkle-batch EVM tx
finalize_batch(&PaymentReceipt, &[Blob])   -> Vec<Address>     // idempotent; resumable
get_data(Address)                          -> Bytes
```

The write path is **split at the payment boundary** so a crash between `pay` and `finalize_batch` never re-pays: the journal (see Vault) records the `PaymentReceipt` the instant the EVM tx lands, and a resumed seal calls `finalize_batch` with the recorded receipt to store any not-yet-stored chunks — `finalize_batch` is idempotent over already-stored addresses and issues no new payment. Implemented over ant-core's **prepare→pay→finalize** surface (`prepare_chunk_payment` / `batch_pay` / `finalize_*`, or the external-signer `PaymentIntent` → `finalize_upload(tx_hash_map)` flow) — **not** `data_upload`/`chunk_put`, whose results carry no payment data (verified: `DataUploadResult = {data_map, chunks_stored, payment_mode_used}`). The `PaymentReceipt` = EVM tx hash(es) + block number (one `eth_getTransactionReceipt`) + **quote preimages** + `PaidChunk.proof_bytes`, persisted per work — everything the v1.1 receipt-verification chain needs, captured from day one. `data_download` serves reads. Tests run on `MockBackend`. Reuse upstream's devnet examples: `start-local-devnet` (25 nodes + Anvil) and `start-devnet-sepolia` (25 local nodes, real Arbitrum Sepolia contracts).

### Definitions & encoding (normative — everything hashes/derives through these)

- **Deterministic CBOR** = RFC 8949 §4.2.1 Core Deterministic Encoding: definite lengths only, shortest-form integers, map keys sorted bytewise on their encoded form, no floats, no indefinite-length items. Encoder crate + exact version pinned in M0 (candidate: `minicbor` with integer keys); golden vectors cross-checked against an independent CBOR implementation. **The decoder MUST reject, as a hard error, any input that is not in this canonical form** — duplicate map keys, non-shortest int/length encodings, indefinite-length items, out-of-order keys, unknown/extra map keys in a fixed schema, and trailing bytes after the top-level item — checked on decode of both the outer bundle/manifest and the inner `body`. Since the sealer authors and self-signs every byte (sealer-as-adversary), this is what upgrades `work_id` from *byte*-binding to *meaning*-binding: without it a sealer could ship, e.g., a body with `sig_policy` duplicated, valid signatures and anchors over those exact bytes, that a first-wins and a last-wins decoder read as different security levels — the CLI and the zero-install WASM page must never diverge on a "valid" bundle.
- **Manifest** = deterministic CBOR `{body: bstr, signatures}`. `body` is an *embedded byte string*: signatures and `work_id` are computed over exactly those bytes as received — **verifiers never re-encode**.
- **`work_id`** = SHA-256(body). **`anchor_digest`** = SHA-256(full manifest bytes, signatures included) — anchoring the signature-bearing bytes binds the signatures into the timestamp. These two names are used exhaustively below; the bare phrase "manifest hash" is banned.
- **`file_id`** = LE64 index into the file table. **`unit_id`** = work-global LE64 ordinal in manifest order (also the id `reveal --units` takes — file-scoped numbering would silently derive identical keys/salts across files). Every label concatenation below is `ASCII-label ‖ LE64(id)`.
- **HKDF-SHA256(W, label, id)**: salt = empty, IKM = W, **info = `u8(len(label)) ‖ label ‖ LE64(id)`** — the length prefix makes the `(label, id) → info` map injective *by construction* (not by the accident that the current labels happen to be prefix-free), so any future label can be added safely. Calls with no natural id use the reserved sentinel `id = 0xFFFFFFFFFFFFFFFF`. Output length per use. (Injectivity is the security-critical property: distinct info ⇒ independent PRF outputs ⇒ keys and salts of different roles never collide.)
- **Content Merkle trees**: two-child, RFC 6962-style unbalanced promotion for odd node counts. Empty file: no fine tree, one empty unit. One-byte file: single-leaf tree (root = leaf).
- **Hash domain tags** (single registry; the first byte of every *commitment / tree / salt-derivation* SHA-256 preimage this spec defines — `work_id` and `anchor_digest` hash raw deterministic-CBOR bytes and are domain-separated by construction, their leading byte being a CBOR header that cannot collide with `0x00`–`0x06`): `0x00` fine-tree leaf · `0x01` fine-tree node · `0x02` unit_commit · `0x03` raw_commit · `0x04` canon_commit · `0x05` path_commit · `0x06` GGM salt-tree child. (Salts are separated by their HKDF labels, not by tags.)

### Canonicalization (v1 — frozen at seal time, recorded in manifest)

- A **work** = one or more files + metadata. Text files (valid UTF-8, or `--force-text`) get a **canonical rendition**: UTF-8, NFC-normalized, LF line endings, no BOM; their unit offsets are **byte offsets into the canonical rendition**. Binary files have no canonical rendition; their offsets are **raw-byte offsets**. The per-file canonicalization descriptor records the kind, the fine tree's presence, its domain (canonical vs raw bytes), **and the exact Unicode data version used for NFC** (e.g. `unicode-16.0.0`). NFC depends on the Unicode version, so the version is frozen per seal, recorded in the descriptor, and the matching normalization table is shipped in `antseal-core` and retained under the format-stability policy; a verifier that must recompute canonicalization (see the raw-mirror check) applies the *descriptor-recorded* version, never "latest" — otherwise an aging honest bundle would false-positive as tampered when the verifier's Unicode tables drift.
- **Units** (= reveal granularity in MVP): default one unit per file; `--split blank-lines` splits text files on blank-line paragraph boundaries (heading-aware splitting is v1.1). Binary files are always single-unit.
- **Fine tree** (the byte-range commitment) is built for **every file by default** — over canonical bytes for text, raw bytes for binary — so the byte-range promise holds for PDFs and datasets, not just text. `--no-fine-tree <glob>` opts out per file (recorded in the descriptor; those files are permanently whole-file-reveal only, and `seal` warns). `seal` prints an estimated fine-tree cost for large files (~5–7 SHA-256 compressions per byte; construction must stream with O(log n) memory).

### Cryptography (v1)

- Per-work master secret `W` (32 B, OS CSPRNG) in the local vault. Everything else — including signing keys — derives from `W` via HKDF with the labels below; the vault stores only `W` + records.
- **`seal_id`**: 16 B, OS CSPRNG, generated at seal start, stored in the manifest body. It exists to keep the AEAD AAD independent of the finished manifest: ciphertext addresses are content-derived, so any AAD that depended on the manifest (e.g. `work_id`) would create a dependency cycle and make sealing impossible. Pipeline order is therefore a clean DAG: `W`/`seal_id` → keys/salts/commitments → unit ciphertexts → unit addresses → manifest body → `work_id` → signatures → plaintext manifest bytes → { `anchor_digest` → anchors } and { `k_m`-encrypt → encrypted-manifest blob → manifest address → `quote_batch`(all blobs) → pay → finalize }.
- **Unit encryption**: `k_u = HKDF(W, "unit-key", unit_id)`; XChaCha20-Poly1305, random 24-B nonce (recorded in the manifest unit table — the single authoritative copy), **AAD = `seal_id ‖ LE64(unit_id)`**. Plaintext = the unit's exact bytes (canonical for text, raw for binary), zero-padded so that **`padded_length = ⌈(true_length + 1) / 256⌉ · 256`** — i.e. always at least one pad byte, so a unit whose content already ends on a 256-B boundary is unambiguous and the empty unit (true_length 0) pads to 256. Stripping is length-first (driven by the manifest's `true_length`), so genuine trailing `0x00` content survives; the verifier recomputes this formula and rejects any unit whose AEAD-plaintext length ≠ `padded_length` (blocks silent over-padding). Padding coarsens each unit's ciphertext length to a 256-B bucket (an observer still learns `⌊true_length/256⌋`); it is cheap defense-in-depth against a passive storage-layer size peek, **not** a full fingerprint defense — per-unit selective disclosure inherently exposes per-unit size, so the vector of bucketed sizes (especially under `--split`) remains a partial fingerprint. The confirmation attack is defeated primarily by (1) randomized AEAD hiding content and (2) the difficulty of *grouping* a work's chunks at all: Autonomi addresses are content-derived and the only artifact enumerating a work's unit addresses — the manifest — is itself uploaded encrypted (below), so a network-only observer cannot tell which chunks belong to one work. Bundle recipients see true lengths by design. The residual per-unit size-fingerprint (exploitable only by an adversary who can both group a work's ciphertexts — via the encrypted manifest, a bundle, the batch-payment tx, or upload-time traffic correlation — and hold a candidate document) is documented in the threat model; the formula is format-version-scoped, so a future version may adopt a coarser scheme (e.g. Padmé, `O(log log n)` leak) without breaking v1 seals if real fingerprinting data ever justifies its permanent storage cost. Ciphertexts upload "public" — they're opaque; randomized AEAD defeats convergent-encryption confirmation attacks by construction.
- **Raw mirror**: where a text file's raw bytes ≠ its canonical rendition (CRLF/BOM/NFD), the raw file is additionally encrypted and uploaded as one extra unit so the original bytes reach storage and `raw_commit` is openable from the network. It is a **full unit-table entry** — `kind = raw-mirror`, its own work-global `unit_id` (assigned in manifest order like any unit, so `k_u`/`unit_salt`/AAD derive normally), byte-range `[0, raw_size)` in the **raw** byte domain, `true_length = raw_size`, `unit_commit`, nonce, address — **exempted by its kind** from the per-file tiling/overlap invariant and from full-reveal concatenation (which apply only to the file's non-mirror, canonical-domain units). Its verify path: `unit_commit` opening always, plus the `file_salt`-keyed `raw_commit` opening when proving exact original bytes. `restore` uses it to return exact originals. Selection rule: **includable only via a whole-file reveal (or `--all`); a bare `--units <mirror-id>` is rejected** so a raw file is never disclosed by a mistyped id.
- **Salted commitments** (hiding + binding; *every* content commitment is salted — an unsalted hash anywhere would re-enable the confirmation attack this design exists to prevent, including against bundle recipients guessing unrevealed files):
  - per-unit: `unit_commit = SHA-256(0x02 ‖ unit_salt ‖ unit_bytes)`, `unit_salt = HKDF(W, "unit-salt", unit_id)` (16 B). **`unit_commit` is present iff the unit is NOT covered by a fine tree** — i.e. only for `--no-fine-tree` whole-file units and raw-mirror units (which live in the raw byte domain the canonical fine tree does not cover). For a fine-tree-covered unit there is **no** `unit_commit`: its content is bound *solely* by `fine_root` (see below), so a per-unit reveal and a v1.1 byte-range reveal of overlapping bytes cannot disagree. Committing the same bytes under two independent salted hashes (`unit_commit` *and* `fine_root`), cross-checked only on a full reveal the sealer may never issue, would let a malicious sealer open byte *i* to X via `unit_commit` for one counterparty and to Y≠X via a `fine_root` range proof for another under one anchored `work_id` — a break of "proof it belongs to what you sealed", frozen unfixably at M0. Hence the single-authoritative-commitment rule.
  - per-file: **two independent salts**, because disclosing a file's path must not compromise its content commitments. `path_salt = HKDF(W, "path-salt", file_id)` (16 B) salts only `path_commit = SHA-256(0x05 ‖ path_salt ‖ path_utf8)` and ships whenever any reveal *touches* the file (so the recipient can verify the path). `file_salt = HKDF(W, "file-salt", file_id)` (16 B) salts the content commitments `raw_commit = SHA-256(0x03 ‖ file_salt ‖ raw_bytes)` and `canon_commit = SHA-256(0x04 ‖ file_salt ‖ canonical_bytes)` (text; enables full-reveal cross-checks since canonicalization is lossy), and is disclosed **only on a full-file reveal**, where the content is shown anyway (zero marginal disclosure). This is load-bearing: `canon_commit`/`raw_commit` sit in the manifest embedded in *every* bundle, so a shared salt would hand any recipient of a single-unit partial reveal an offline full-file confirmation oracle (recompute `canon_commit` for a guessed document — exactly the confirmation attack this design exists to prevent). `fine_root` is unaffected (its salts derive from the independent fine-seed). **File paths live in the vault, not the manifest**: disclosed (with `path_salt`) per touched file at reveal time; bundle recipients see unrevealed files only as committed placeholders ("file #3, 48 KB"). Structure metadata (file count, sizes, unit boundaries) *is* visible to bundle recipients — docs state this.
  - **fine tree with GGM salt derivation** (range-proof-friendly; this replaces flat per-index salts, which would have forced 16 B of salt per revealed byte — and whose seed, if ever disclosed, would turn `fine_root` into an unsalted whole-file commitment). Let `n` = the file's size field (leaf count); **fine-tree leaf `i` commits byte `i` of the exact same bytes committed by `canon_commit` (text) / `raw_commit` (binary)** — this binding is normative and prevents a sealer equivocating between a per-unit reveal and a v1.1 byte-range reveal of the same `work_id`. Salt derivation: `s_root = HKDF(W, "fine-seed", file_id)` (32 B); the **GGM salt tree is a complete binary tree of depth `d = ⌈log₂ n⌉` (2^d leaf slots), independent of the content Merkle tree's shape**; children `s_{v‖b} = SHA-256(0x06 ‖ s_v ‖ b)` for bit b ∈ {0x00, 0x01}; **leaf `i` is reached from `s_root` by the bits of `i` MSB-first (bit d−1 first); slots `i ≥ n` are unused**; `salt_i` = leaf-`i` seed truncated to 16 B (`d = 0`, `n = 1`: `salt_0 = s_root[..16]`). Content leaves: `leaf_i = SHA-256(0x00 ‖ salt_i ‖ LE64(i) ‖ byte_i)`; two-child SHA-256 Merkle with `0x01` node prefix, RFC-6962 unbalanced promotion (§ Definitions). Only `fine_root` enters the manifest. MSB-first indexing makes any contiguous range a dyadic decomposition covered by its **minimal GGM subtree cover** (≤2·⌈log₂ n⌉ seeds ≈ 1.7 KB even at n = 10⁸) plus boundary Merkle paths; out-of-range salts stay pseudorandom (puncturable-PRF hiding). **`fine_root` is the sole content commitment for a fine-tree file**: *every* reveal of covered bytes — a whole-unit reveal (MVP) or a byte-range reveal (v1.1) — is a leaf-range opening verified against `fine_root`, so there is exactly one authoritative content value per byte and no cross-mode equivocation is possible (standard-model, SHA-256 collision-resistance). Unit boundaries are byte offsets (leaf-aligned), so an MVP per-unit reveal is just the special case where the range is a whole unit — no mid-grapheme handling, which is the part genuinely deferred to v1.1 (arbitrary-range *selection* + rendering, not this verification, which exists and is M0-tested). A per-unit/range reveal ships the revealed leaves' bytes + the minimal GGM sub-cover of *exactly those leaves* + the boundary Merkle paths; the verifier derives the in-range salts, rebuilds the leaves, and checks the boundary path up to `fine_root`. **Normative: the cover MUST be leaf-exact** (deepest single-leaf nodes at the range boundaries) — a merely-valid dyadic cover whose node spans an unrevealed real leaf `j < n` would disclose `salt_j` and reopen the per-byte confirmation attack; **no seed that is an ancestor of any unrevealed leaf ever leaves the vault** (so the fine-seed `s_root` itself is conveyed only on a full-file reveal, where all leaves are revealed and the verifier recomputes `fine_root` from the revealed bytes). Every disclosed 32-B seed (`s_root`, GGM covering seeds) and 32-B boundary node hash is length-checked by the verifier alongside the 16-B salts.
- **Author signature**: hybrid **Ed25519 + ML-DSA-65** over the body bytes, both binding the fixed context string **`"antseal-manifest-v1"`** (ML-DSA-65 via its FIPS-204 `ctx` parameter; Ed25519 by signing `ctx ‖ 0x00 ‖ body` — a domain prefix folded into the pre-image), frozen at M0 so a signature can never be lifted into another context. **Verification MUST be strict/canonical and is a conformance requirement for every verifier (CLI, WASM page, third parties) so they cannot diverge on the same frozen bundle**: Ed25519 per RFC 8032 `verify_strict` (reject non-canonical `S ≥ L`, reject small-order/non-canonical `R`/`A` — Ed25519 is otherwise malleable and only EUF-, not SUF-, CMA); ML-DSA-65 rejecting any non-canonical/out-of-range signature encoding (hint/`z` bounds). Signing keys derive from `W`: Ed25519 seed = `HKDF(W, "sig-ed25519", sentinel)`, ML-DSA-65 seed ξ = `HKDF(W, "sig-mldsa65", sentinel)` (FIPS 204 keygen expands a 32-B seed) — independent (distinct labels), per-work by construction. **`sig_policy`** (ordered list of required algorithm IDs) is a body field: it MUST be a non-empty, duplicate-free list of registered algorithm IDs (rejected at parse time otherwise, so a signature-less manifest can never verify vacuously), and the **present signature set MUST equal the policy set** — the verifier validates every listed signature and hard-fails on any that is missing, invalid, *or present but unlisted* (so a hybrid manifest never passes on one good signature, and the verdict label "hybrid (PQ)" vs "Ed25519-only" is unambiguous). Fallback if ML-DSA fails the M0 WASM probe: ship `sig_policy = [ed25519]` (format unchanged — the slot is reserved). Anti-downgrade: the policy sits in the signed, anchored body, so an existing hybrid manifest cannot be downgraded without breaking its anchors; a fresh Ed25519-only forgery is a new work with its own (later) timestamps. Verdicts label "hybrid (PQ)" vs "Ed25519-only". Crates: `ml-dsa = "=0.1.1"` (pre-1.0, unaudited, two Jan-2026 advisories — pin exact, track RUSTSEC), `fips204 = "=0.4.6"` (dormant since 2024-12) as fallback; `ed25519-dalek` pinned exactly (2.x vs the three-week-old 3.0.0 decided at M0).
- **Manifest body fields**: format version, app version, `seal_id`, title, claimed time (informational only), pubkeys, `sig_policy` (non-empty), file table {`path_commit`, `raw_commit`, `canon_commit`?, `size` (leaf count / tiling domain = canonical bytes for text, raw bytes for binary; a text file's raw byte count is carried by its raw-mirror unit's `true_length`), canonicalization descriptor, `fine_root`?, unit table {`unit_id`, `kind` (normal | raw-mirror), byte-range, `true_length`, `unit_commit`? (present iff the unit is not fine-tree-covered — see per-unit commitment), nonce, ciphertext network address}}. Raw-mirror units are ordinary unit-table entries distinguished by `kind` (no separate link field). **The uploaded manifest copy is encrypted**: `k_m = HKDF(W, "manifest-key")`, XChaCha20-Poly1305, random nonce, AAD empty — the network stores only opaque AEAD bytes (title, paths-as-commitments, sizes, pubkeys never appear in plaintext on the network). **Anchors bind `anchor_digest` over the *plaintext* manifest bytes** — bytes anchored ≠ bytes stored; bundles embed the plaintext manifest plus the **manifest storage record** {address, nonce, `k_m`} for persistence checks (`k_m` discloses nothing beyond the manifest the bundle already contains).
- **Security assumptions (frozen at M0 — a permanent format rests on these; stated so the freeze is a signed-off decision, not an implicit one):**
  - **Binding** of every commitment (`unit_commit`/`raw_commit`/`canon_commit`/`path_commit`/`fine_root`) and of `work_id`/`anchor_digest` is **standard-model SHA-256 collision-resistance (~128-bit)** — the permanent sealer-equivocation bound. No hash agility exists; a format-version hook is reserved should a wider hash ever be needed.
  - **Hiding** (confirmation-attack resistance, incl. low-entropy single-byte fine-tree leaves) is a **random-oracle-model** property of secret-prefix salted SHA-256 with a 128-bit secret salt — it is **not** implied by collision-resistance and would not survive a SHA-256 that is collision-resistant but not a PRF. Multi-target hiding erodes to ~2^128/K over K exposed commitments; 128-bit salts are the intended margin (comfortable).
  - **GGM range/leaf hiding** assumes SHA-256 is a secure length-doubling PRG on the fixed 34-B single-block input `0x06 ‖ seed ‖ b` (equivalently SHA-256-as-RO) — the same message-keyed-PRF assumption class as XMSS/SPHINCS+ tweakable hashes. Length-extension is inapplicable (all commitment/tree/salt preimages are fixed-length or equality-compared, never used as a keyed-prefix MAC). Puncturing soundness depends on the leaf-exact-cover / no-ancestor-seed rule above.
  - **AEAD is confidentiality-only.** XChaCha20-Poly1305 is not key-committing (invisible-salamanders / partitioning class); this is acceptable because **no verdict-bearing check relies on a ciphertext decrypting to a unique plaintext** — all content/identity binding is via the salted SHA-256 commitments and the signatures, and storage-linkage/`--live` bind *ciphertext* bytes (address recomputation, byte-compare). **A future refactor MUST NOT drop a content commitment in favor of trusting the AEAD.**
  - Signature unforgeability = Ed25519 (strict) SUF-CMA + ML-DSA-65; the hybrid requires both and is non-downgradable (policy inside the signed+anchored body).

### Anchoring (verification in `antseal-core`; `antseal-anchor` is the network side)

- **OTS**: stamp `anchor_digest` against ≥2 public calendars; store pending `.ots`. Upgrades to a Bitcoin attestation are attempted **opportunistically on every CLI invocation** plus `status --upgrade`. For each upgraded OTS anchor, bundles embed the attested block **height and the 80-byte block header** (+ fetch date). A lone embedded header carries no *offline* time guarantee — its proof-of-work is self-referential (an attacker picks its own `nBits`, so a minimal-difficulty forged header mines in seconds) and a single header cannot be chained to any pinned reference offline. The design is therefore deliberately **online-gated for Bitcoin**: offline, an upgraded OTS anchor renders state **`attested`** ("ops commit `anchor_digest` to the merkle root of Bitcoin block H (header embedded); a provable time requires `--online` confirmation") — informative but **not headline-eligible offline**, so a forged header can never produce an offline headline time (this is what closes the wholesale-forged-bundle attack without a chain-of-headers in every bundle). `--online` fetches block H from the must-agree esplora endpoints, checks the embedded header matches and reads its timestamp, and **promotes the anchor to `proven` (headline-eligible)** — normally the earliest, strongest anchor. A header that fails the online match, or an `.ots` whose ops don't commit `anchor_digest`, is the `forged Bitcoin attestation/header` tamper case (`invalid`). The **offline** headline therefore comes from RFC 3161 TSA tokens (below), which *are* fully offline-verifiable against pinned roots. Crate reality (verified): `opentimestamps` 0.2.0 (2023; the crates.io name — the GitHub repo is `rust-opentimestamps`) is a codec only; the calendar HTTP client (submit, upgrade polling, attestation merge) is **committed in-house M2 work (~1–2 weeks)**, reusing the crate solely as the wire-format layer.
- **RFC 3161**: build DER `TimeStampReq` (messageImprint = `anchor_digest`, nonce, certReq), POST to a configurable TSA list — **defaults: FreeTSA (`https://freetsa.org/tsr`) + DigiCert (`http://timestamp.digicert.com`)**; documented alternates with recorded caveats: zeitstempel.dfn.de (non-commercial terms), Sectigo (~15 s spacing), SwissSign (~10/day). Verification (in `antseal-core`, WASM-safe): full CMS SignedData — signed-attributes check, messageImprint + nonce match, ESSCertID, EKU `id-kp-timeStamping` — with the chain validated to a **pinned TSA root store compiled into `antseal-core`** (versioned, updatable; bundle-embedded chains supply intermediates only — a chain that only closes against bundle-supplied roots renders "internally consistent only", never "proven"). **Chain validity is evaluated at the token's genTime** (long-term validation): "valid at stamping; certificate since expired" renders distinctly from invalid — aging bundles must not silently rot. Must support **ECDSA P-384** TSA certs (FreeTSA's 2026 cert) alongside RSA. Effort note: no turnkey pure-Rust CMS verifier exists (`cms` parses only; `x509-cert` has no path validation) — single-path validation over pinned roots is explicitly budgeted M2 work.
- **Arbitrum receipt**: captured in full at payment time via the batch APIs (tx hashes, block number, quote preimages, proof_bytes) and stored in the vault. **MVP verdicts render it as "supporting evidence — no independently proven time"**: no on-chain datum contains `anchor_digest`; the full chain (recompute chunk addresses from manifest/ciphertext bytes via deterministic `self_encryption`, match quote preimages, confirm quote hashes in tx calldata over RPC) is specced for v1.1 — capture is complete from day one, so no reseal will ever be needed. Bundle inclusion is **opt-in** (`reveal --include-receipt`): the receipt exposes the paying wallet and links all of a user's seals (see Risks).

### Reveal bundle (`.sealproof`, versioned deterministic CBOR)

Self-contained by design — verification must not require Autonomi access. Contents: plaintext manifest bytes + manifest storage record + per-anchor artifacts (status, `.ots` + embedded Bitcoin header where upgraded, TSA tokens + intermediate certs, fetch dates; receipt only if opted in) + per revealed **fine-tree-covered** unit {`unit_id`, `k_u`, embedded ciphertext, the leaf-exact **GGM sub-cover** of the unit's leaf range, **boundary Merkle paths** up to `fine_root`} (verified against `fine_root`) + per revealed **non-covered** unit — `--no-fine-tree` or raw-mirror — {`unit_id`, `unit_salt`, `k_u`, embedded ciphertext} (verified against `unit_commit`) + per **touched** file {path, `path_salt`} + per **fully revealed** file {`file_salt`, **`s_root`** (the full `[0, n)` cover; discloses nothing, since every leaf is revealed)} (and its raw-mirror unit when proving exact original bytes) + (v1.1) sub-unit *arbitrary*-byte-range covers + their boundary paths. Nonces come from the manifest (single source of truth). The GGM sub-cover of a covered unit contains only descendant seeds of that unit's *revealed* leaves — never `s_root` or any ancestor of an unrevealed leaf — so it is not a partial-reveal disclosure of `file_salt`/`s_root`.

**Two proof layers, rendered distinctly** (the evidence never depends on Autonomi):

1. **Evidence layer** — decrypt → strip/verify zero padding → **bind the bytes to the manifest's single content commitment**: for a fine-tree-covered unit, derive the in-range leaf salts from the GGM sub-cover, rebuild the leaves, and verify the boundary path up to `fine_root`; for a non-covered (`--no-fine-tree` / raw-mirror) unit, recompute `unit_commit` and match — → structural invariants → `sig_policy` check → anchor checks against pinned roots. This alone carries the evidentiary verdict; storage is the product's bonus, not its proof.
2. **Storage-linkage layer** — the embedded ciphertext must derive the manifest's ciphertext network address (deterministic `self_encryption` address recomputation inside `antseal-core`, fully offline); `--live` re-fetches from Autonomi and byte-compares to prove persistence.

**Verifier structural invariants** (the sealer is an adversary too — positions and sizes are sealer-authored): **every disclosed salt/seed/node hash has its exact spec length** — `unit_salt`/`path_salt`/`file_salt` = 16 B (blocks shift-malleable openings across the salt/message boundary), `s_root` and every GGM covering seed = 32 B, boundary Merkle node hashes = 32 B; a revealed unit's manifest **`true_length` = its byte-range width = its AEAD-plaintext length after padding strip** (so a unit cannot claim more span than it reveals); padding conforms to the `padded_length` formula and is all-zero beyond `true_length`; **non-mirror** unit byte-ranges sorted, non-overlapping, and exactly tiling [0, size) per file (raw-mirror units are exempt by `kind`); on a full file reveal, the concatenated non-mirror unit bytes must hash to `canon_commit` (text) / `raw_commit` (binary) and, using the bundled `s_root`, the verifier MUST rebuild the whole fine tree from those bytes and match `fine_root`. **Raw-mirror ↔ canonical binding**: whenever a reveal discloses *both* a file's raw-mirror bytes and its canonical content (every full reveal carrying a raw mirror), the verifier MUST recompute `canonicalize_v(raw_mirror_bytes)` — `v` = the file descriptor's recorded Unicode/canonicalization version — and require it to equal the validated canonical bytes; otherwise a sealer could co-timestamp an "original" that does not canonicalize to the sealed content. **Partial-reveal isolation**: for any file only *partially* revealed, the bundle MUST NOT contain that file's `file_salt` or `s_root` (so `canon_commit`/`raw_commit`/`fine_root` stay unopenable); the leaf-exact GGM sub-cover a covered per-unit reveal *does* carry is permitted (it holds only descendant seeds of revealed leaves). Every reveal displays position + total size (anti-out-of-context guardrail); unrevealed units render as sized blackout blocks; unrevealed files render as committed placeholders (size only, path withheld).

**Format stability (normative)**: every released manifest/bundle format version remains verifiable by all future CLI and page releases; per-version golden vectors are retained in CI indefinitely; the hosted page supports all released versions.

### Verifier web page

Plain HTML/JS + `antseal-core` WASM (which contains *all* verification, anchors included). Offline-first: full local verification. **Verdict taxonomy per anchor** (one authoritative wording set; M3 snapshot-tests it); **headline-eligible** states are tagged [H]:

- `proven` **[H]** — a TSA token valid against the pinned root store, or an OTS anchor `--online`-confirmed against Bitcoin block H.
- `valid-at-stamping-cert-since-expired` **[H]** — TSA token whose signature verifies and whose chain was valid at its genTime but whose cert has since expired; still carries its independently-proven stamping time (aging bundles must not silently rot), so it remains headline-eligible.
- `attested` — upgraded OTS, header embedded, **not** headline-eligible offline; `--online` promotes it to `proven`.
- `pending` — OTS not yet upgraded ("not yet independently provable — ask the sealer to run `status --upgrade`"; the same-day-reveal case every demo hits).
- `internally-consistent-only` — a well-formed token/attestation that does not chain to a pinned root (TSA) or match online (OTS): cryptographically well-formed but not independently anchored; never headline-eligible.
- `invalid` — signature/op check fails.
- `absent` — anchor not present.

The Arbitrum receipt is **not an anchor** and renders in a separate class, "supporting evidence — no independently proven time" (never headline-eligible). **One headline**: "Existed no later than \<earliest headline-eligible time\> (source)". Claimed time renders visually subordinate, labeled "asserted by sealer — NOT verified", and never enters the headline. Divergence >48 h between *headline-eligible* anchors is flagged. Zero headline-eligible anchors → loud "UNANCHORED — integrity and signature only, no provable time". A normal seal never hits this offline: the minimum-anchor policy guarantees ≥1 TSA token, which is `proven` (headline-eligible) offline. It arises only for `--force-degraded`/`--no-anchor` seals, or a bundle carrying only a `pending`/`attested` OTS — where `--online` or a later `status --upgrade` then supplies the headline. Online mode: **two pinned default endpoints per source, results must agree** (esplora-style: blockstream.info + mempool.space; two public Arbitrum RPCs), user-overridable, rendered as an advisory overlay distinct from the offline cryptographic verdict. No framework, no build beyond `wasm-pack`.

**Page provenance** (the page is itself a trust point — any host can serve lying JS): reproducible `wasm-pack` build with a published SHA-256 and signed releases; **one canonical URL** used in all docs and printed by the CLI in `reveal` output; the page footer displays its own build hash + "for high-stakes verification, run `antseal verify` and compare verdicts". Page hosting/deploy is an M3 deliverable.

### Vault

`~/.antseal/`: config + per-work records (`W`, seal journal, receipts, `.ots`, TSA tokens, addresses, paths, costs), encrypted at rest with a passphrase. Because a stolen vault **retroactively and permanently decrypts public, undeletable ciphertexts with no possible rotation**, the KDF is hardened accordingly: **Argon2id, m ≥ 256 MiB, t = 3, p = 1 (default), random 16-B salt** — with `scrypt N ≥ 2²⁰` as an alternative — the algorithm id + full parameters live in the vault header, and **the entire KDF header is bound into the vault AEAD as AAD** so a parameter downgrade (e.g. lowering `m`/`N`) is a detected authentication failure, not a silent weakening. `init` enforces a passphrase-strength floor and offers a high-entropy keyfile / OS-keystore wrap for `W`. **The Arbitrum wallet key lives inside the encrypted vault** but under its *own* sub-key (decoupled blast radius; external-signer support may come later). `zeroize` on `W`, unit keys, and passphrase buffers (documented caveat: the WASM verifier cannot guarantee this for bundle-supplied keys in browser memory). `vault export`/`import` for encrypted backup. **Docs and CLI must nag on both failure modes**: *loss* (lose the vault and backup = lose reveal/restore ability forever; the sealed data itself stays safely unreadable) and *theft* (retroactive decryption of permanently public ciphertexts — no rotation exists; treat the passphrase and any export as a long-term high-value key).

**Seal journal**: before payment, draft state persists in the vault as the **staged ciphertext bytes** of every unit (plus each unit's nonce and target address); the `PaymentReceipt` is journaled the instant the EVM tx lands, *before* `finalize_batch`. **A unit's `(k_u, nonce)` pair is single-use — it encrypts exactly one plaintext, ever.** Re-running `seal` on an interrupted work **re-uploads the byte-identical staged ciphertexts** and, if a receipt is journaled, calls `finalize_batch(receipt, blobs)` to store the not-yet-stored chunks without re-paying (`finalize_batch` is idempotent over already-stored addresses). Resume **never re-encrypts**: if a source file changes it can no longer reproduce the anchored `unit_commit`/`fine_root`/addresses, and re-encrypting a changed plaintext under the *recorded* nonce would be catastrophic `(k_u, nonce)` reuse (two ciphertexts under one keystream ⇒ plaintext-XOR and Poly1305-key recovery ⇒ forgery). So if staged bytes are unavailable, the in-progress seal is **abandoned** — a fresh seal starts with a new `seal_id` and freshly drawn nonces (never the journaled nonce table), forfeiting any already-made payment as a deliberate safety-over-cost choice (rare: needs disk loss of staged bytes *after* pay). Resume never rebuilds or re-signs the manifest (it is anchored pre-pay). `list` shows `incomplete` works.

### CLI surface (MVP — this list is canonical; the flows above are examples of it)

## Risks & mitigations

- **ant-core churn (weekly-to-biweekly)** → exact pin + batch-first `StorageBackend` isolation + mock-first tests; bumps are deliberate events; re-verify the pin (published 4 days before this revision) at M0 start.
- **Autonomi network youth (1.0→2.0 was a full data reset)** → evidence validity never depends on Autonomi: bundles self-contained, anchors are Bitcoin/TSA; storage permanence is the product's bonus, not its proof. Only one pre-release mainnet exposure exists (M4 smoke seal) — accepted.
- **Receipt anchor not independently verifiable in MVP** → demoted to "supporting evidence" in every verdict and doc; capture is complete so the v1.1 chain needs no reseal.
- **OTS pending window / calendar death; TSA churn and cert expiry** → minimum-anchor seal policy (≥1 TSA token or `--force-degraded`); opportunistic upgrades on every CLI run + `list` nags; pinned roots + genTime LTV ("expired ≠ invalid"); ≥2 TSAs with named defaults and documented alternates.
- **PQC crate maturity** (`ml-dsa` 0.1.1 unaudited, two Jan-2026 advisories; `fips204` dormant) → exact pins, RUSTSEC tracking, M0 WASM probe, reserved-slot Ed25519-only fallback made non-breaking by `sig_policy`.
- **Vault loss AND vault theft** → export nag on first seal; loud docs for both; pinned scrypt params with header agility; wallet key inside the vault; `zeroize`.
- **Wallet linkability** (receipt links every seal to one wallet, and that wallet to an identity) → receipt excluded from bundles by default (`--include-receipt` to opt in); wallet-hygiene docs (fresh address per work/client); threat-model section.
