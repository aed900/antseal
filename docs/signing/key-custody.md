# Release signing key — custody

Normative custody rules for the one long-lived Ed25519 key that signs antseal
releases. The mechanism, and every rule restated here, is decided by
[D71](../decisions/D71-binary-signing-mechanism-and-key-custody.md); this
document is the operational half and is **append-only** — a change is a dated
entry at the bottom, never an edit to what is above it.

> **STATUS, 2026-08-18: no key exists yet.** Nothing in this document has been
> executed against a real project key. The keypair is generated by the
> maintainer following [`maintainer-key-procedure.md`](maintainer-key-procedure.md),
> and the first line of §7's log records the day that happens. Until then every
> statement here is a rule, not a description.

## 1. The mechanism, in one paragraph

One long-lived Ed25519 keypair, held by the maintainer, used with
[minisign](https://jedisct1.github.io/minisign/). Signing is a **local act** on
the maintainer's own machine. The secret key is never on a CI runner, never in
a GitHub secret, never in a hosted key-management service, and never in this
checkout (D71 §2 R1, §2 R7.2). `rsign2` is the sanctioned interoperable
alternative for producing signatures; a release signed with either tool is
verified by either.

## 2. Holder, location, and the one prohibited form

| | |
|---|---|
| **Holder** | the antseal maintainer, personally. No second holder, no escrow, no shared custody. |
| **Working location** | `~/.minisign/minisign.key` on the maintainer's machine — minisign's own default path (D71 §2 R7.2). |
| **Never** | any CI runner, any GitHub Actions secret, any KMS or cloud secret store, any file this repository tracks, any backup that is online. |

**The key is passphrase-protected. `-W` is forbidden** (D71 §2 R7.1). minisign
wraps the key with **scrypt** at libsodium's `OPSLIMIT_SENSITIVE` /
`MEMLIMIT_SENSITIVE`, a 32-byte salt and a BLAKE2b-256 checksum — the same
primitive family, at the strongest published parameter set, that
[D40](../decisions/D40-vault-kdf-selection.md) chose for the antseal vault.
Nothing weaker is acceptable.

Three reasons, none of which depends on any checker noticing:

1. An unencrypted key is a plaintext Ed25519 secret at rest on the maintainer's
   machine **and in every offline backup of it** — and §4 mandates two.
2. The key **can never be withdrawn once published** (§6). A single read of the
   file is therefore unbounded in time, with no recovery step to fall back on.
3. scrypt at that parameter set costs the maintainer one passphrase entry per
   signature and costs an attacker who has the file a great deal more.

`scripts/sign-release.sh` **refuses to run** against a key whose KDF field says
it is unwrapped. The refusal reads the key struct's `kdf_alg` field rather than
matching its header line, because the header is free text that `-c` replaces
outright — D71 §B R3 is the reasoning, and D71 §1.3 row 4 is the measurement
behind it.

The passphrase is generated and stored the way the vault passphrase is, and it
is **not** the vault passphrase.

## 3. The key is used for nothing else

Not an SSH key, not a git commit-signing key, not the vault key, not a wallet
key (D71 §2 R7.4). Cross-protocol reuse of an Ed25519 key is the
domain-separation failure this project designs against everywhere else, and it
is not going to be introduced at the release boundary.

## 4. Backup

- **Two** offline backups of the passphrase-wrapped key file, on **separate
  media**, in **separate physical locations**. Offline means offline: not a
  synced folder, not a cloud drive.
- The **passphrase** recorded by whatever means the vault passphrase is
  recorded by, and not stored with either backup.
- **The public key is backed up too.** It is recoverable from the secret key
  with `minisign -R`, and from nothing else — losing both is losing the
  identity, and every published signature becomes uncheckable by anyone who did
  not keep a copy.

## 5. Loss, and why it is the cheap failure

If the secret key and all backups are gone, no further release can be signed
under it. **Every previously published signature remains valid and checkable.**
A new keypair is generated and §6's rotation runs.

Loss is more likely than compromise, and the asymmetry is deliberate: the
scheme is arranged so that the likely failure is survivable and the unlikely
one is at least detectable (§8).

## 6. Rotation — and the fact that withdrawal does not exist

**minisign has no revocation, no expiry, no key hierarchy and no
cross-signing.** This is a property of the scheme, not an oversight in the
tool, and not something this project can engineer around. It is written down
here so that nobody later assumes otherwise, and D71 §2 R11 forbids the release
documentation implying any of those mechanisms exists.

**The key is long-lived and is NOT rotated on a schedule.** Routine rotation is
refused: every rotation destroys, for every user who pinned the old key, the
one property worth the most — that a user who pinned at v0.1 detects a
substituted v0.2 even under total compromise of the hosting at that later
moment. Rotation happens for exactly two reasons: **loss** (§5) and **suspected
compromise** (§7).

The procedure, in order:

1. Generate the new keypair (`maintainer-key-procedure.md` §1).
2. **Anchor the new public key before publishing it** (§8), so its age is on
   record from its first day.
3. **If — and only if — the old key is still held and is not the thing that was
   compromised**, sign the new public key with the old one:

   ```
   minisign -Sm minisign.pub -t 'antseal key rotation <YYYY-MM-DD> supersedes <old key id>'
   ```

   published as `minisign.pub.minisig`. This is the only continuity mechanism
   available and **it is worth nothing in the compromise case** — an attacker
   holding the old key can mint exactly the same statement. It helps in the
   loss case only, and any documentation that shows it must say which.
4. Update **all four** publication locations in one act (`README.md`, the
   page footer, the DNS `TXT` record, the release), and add a §9 entry
   recording the old key id, the new key id, and the date.
5. Announce out of band on whatever channel D72 establishes.

## 7. Compromise response

**There is no mechanism that reaches a user who has already pinned the
compromised key.** All that can be done is: announce, rotate (§6), and state a
date.

And because a compromise's start is rarely known, **every release signed by
that key must be treated as suspect for the key's whole lifetime**, not from
the date of discovery. That is a genuine weakness of the chosen mechanism. It
is accepted deliberately, in exchange for the trust-on-first-use property §6
protects and the anchor in §8, and D71 §A R2 records that the margin over the
alternative is narrow.

Immediate steps, in order:

1. Stop signing. Do not publish anything further under the key.
2. Generate and anchor a new keypair (§6 steps 1–2).
3. Publish a dated statement naming the old key id, saying that its start of
   compromise is not known, and saying that every release under it is suspect.
4. Update all four locations (§6 step 4) and log it in §9.

## 8. What the anchor is for, and what it is not

The public key is timestamped with this project's own OpenTimestamps client and
the proof published beside it as `minisign.pub.ots` (D71 §2 R6).

**What it buys:** anyone can establish that this exact 42-byte key existed
before a specific Bitcoin block. An attacker who substitutes a key next year
can anchor theirs only as of next year, so a silent substitution becomes
publicly detectable, from a trust root that is neither this project's nor its
host's. It publishes an opaque digest and nothing else — no repository name, no
owner, no commit.

**What it does not buy, so nobody trusts it past its limit:** an anchor shows a
key is *old*. It never shows the key is *the maintainer's*. It does not help a
first-time user who has no expectation about the project's age, it defeats
substitution-after-the-fact rather than an adversary present from day one, and
checking it needs an OpenTimestamps verifier.

**The proof has two states and the release must say which one it is in.** A
freshly submitted proof is *pending* — attested by calendar servers, not yet by
Bitcoin — and becomes *upgraded* only after a later pass. D71 §A R4 therefore
says to stamp the key **a few days before** a release, so the release ships an
upgraded proof. A release that ships a pending proof must label it pending.

## 9. Where the public key is published, and what each place is worth

Four locations. The column that matters is the third one.

| location | independent of the release host? | what it is for |
|---|---|---|
| `README.md` | **No** — same account, same hosting | discovery |
| the page footer at `https://antseal.org/` | **No** — the page, the README and the release assets are one account, and the page's certificate chain and the release-asset host's are the same issuer path | discovery |
| `minisign.pub` as a release asset | **No** | so someone holding the release directory can compare key ids |
| **`TXT` record at `antseal.org`** | **Yes** — changing it needs the domain registrar account, which is a different account from the one that hosts the code | **the only pin that survives a compromise of the code host** |
| the anchored copy (§8) | **Yes** — Bitcoin | evidence the key is not new |

> **TODAY THERE IS NO INDEPENDENT PIN.** Measured 2026-08-18: `dig TXT
> antseal.org` returns nothing — the zone has no `TXT` records at all. Until
> the record in `maintainer-key-procedure.md` §2 is created, the "independent"
> column above is empty in practice, and a first-time user's trust in the key
> reduces to trusting the code host. D71 §5.1 requires this document to say so
> out loud rather than describe the intended end state.

Two further limits, recorded rather than glossed:

1. **`antseal.org` is not DNSSEC-signed.** Measured 2026-08-18: the `DS` query
   returns no answer and responses do not carry the authenticated-data flag. So
   the `TXT` pin is **not** protected against an on-path attacker or a hostile
   resolver. It is independent of the threat this scheme is actually about —
   compromise of the code-hosting account — because forging it needs the
   registrar account instead. Claiming it defends both would be false.
2. **The README pin is not anonymously readable while the repository is
   private.** Measured 2026-08-18: the repository is still private. Going
   public makes that pin *readable*; it does not make it *independent*, because
   whoever can replace the binary can replace the README in the same act under
   the same credential (D71 §A R6).
