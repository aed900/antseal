### S31 — No journal-backed `ReceiptSink` exists, so D37's per-sub-batch durability is unreachable and S18's between-sub-batch kill row cannot be written
- Milestone: M1
- Size: M
- Deps: S27 (the same obligation, from the construction side), S12/S10 (whose journal write is the current one), D37
- Discovered by: **S18** (2026-08-02), while implementing accept row 2's kill half against a live devnet.
- Problem: D37 Decision 2 says each sub-batch receipt is journaled **inside** `pay`, before the next tx is submitted, so a crash between sub-batch txs cannot lose money that has already moved. The *seam* for that exists and is now structurally unavoidable (U36's `ReceiptSink` argument to `SealBackend::connect`, asserted live by S17). **What does not exist is any implementation that writes durably.** The whole tree has exactly three `ReceiptSink` impls: `ReadOnly` (which logs an error and drops the receipt), a counting double in `backend.rs`'s tests, and S18's `CapturedReceipts` (in-memory). The pipeline journals the receipt itself, at `resume.rs` `put_receipt`, **after `pay` returns** — so today the hook fires, is observed, and nothing durable happens.
  Consequences, in order of severity: (i) a crash between sub-batch txs of a multi-tx payment loses every receipt so far, and the resume re-quotes, re-consents and **pays for the already-paid sub-batches again** — S16 measured exactly this cost in the single-tx case and it is why the hook is a requirement rather than an optimisation; (ii) S18 accept row 2's kill half is therefore untestable — asserting "no sub-batch is ever re-paid" would fail, correctly, against the code as it stands; (iii) the D37 guarantee is currently a documented property with no implementation behind it, which is the F41 class.
- Do: decide and implement how a `Send + Sync + 'static` sink reaches the vault journal. `VaultJournal` is neither (it borrows the unlocked vault and holds a `RefCell` around the RNG), which is precisely why U36 made the seam a trait rather than `&VaultJournal` — but no one has since closed the loop. Options, none free: (a) a sink owning its own `WorkStore` session behind a `Mutex`, which needs the vault key available to a `'static` value and re-examines U5's single-writer lock under concurrent access from inside `pay`; (b) a channel-backed sink whose receiving half the pipeline drains and journals synchronously between sub-batches, keeping the write on the pipeline's side where S10 wants it; (c) narrow D37's claim to "the hook exists for callers who need it" and accept the re-pay window for multi-tx payments, recording the cost — the honest option only if (a) and (b) are genuinely unaffordable.
- Accept:
  - A recorded decision (this is a D37 amendment either way — it either implements the stated guarantee or narrows it).
  - If implemented: S18 gains the between-sub-batch kill row — real SIGKILL inside `pay` at a forced cap, resume, **exactly one tx per sub-batch on Anvil**, quote→tx map complete, balance delta = quote once. The suite already has the forced-cap seam (`SealBackend::with_max_transfers_per_tx`), the child-process SIGKILL harness and the Anvil probe, so the row is small once the sink exists.
  - S27 closes with it, or is explicitly left open with what remains.
- Notes: not decided inside S18 — the sink's shape is a real design question touching U5's lock, S10's journal ownership and D37's text, and the gate's job was to find that it is missing, not to pick the answer alone. S18 ships the no-kill half of the row (protocol, per-sub-batch capture, tx accounting, all Anvil-verified) and says at the assertion site why the kill half is absent.

- U: encrypted vault with per-work record storage API (journal records, receipts, paths, addresses, costs — layout U's, content mine); vault-held Arbitrum wallet key handle for payment signing (keygen/import/address ops are S5's deliverable to U11); consent/confirmation and re-consent hooks; CLI flags (`--network`, `--no-anchor`, `--yes`, `--dry-run`, `-o`) wired to pipeline/restore; `list`/`show` rendering of `incomplete`/abandoned state and per-work cost; `vault export`/`import` for S19.
- C: WASM-safe primitives in `antseal-core` — HKDF (`k_u`, `k_m`), XChaCha20-Poly1305 encrypt/decrypt with AAD, padding formula + length-first strip, nonce drawing, salted commitment recompute (`raw_commit`/`canon_commit`) for restore verification.
- G: canonicalization + unit splitting delivering unit plaintext bytes, byte-ranges, raw-mirror detection, and canonicalization descriptors that feed staged encryption and restore.
- F: manifest build/encode/decode with the unit table (nonce, `true_length`, byte-range, ciphertext network address fields accepting S4 addresses), encrypted-manifest blob + manifest storage record, UNANCHORED/empty-anchor representability with M0 golden vectors (synthetic addresses acceptable until S4 lands).

- R: M0 library verification entry (structural/commitment/signature checks incl. absent-anchor → UNANCHORED verdict) callable by the M1 E2E; M3 storage-linkage and `verify --live` orchestration consuming S4's address recomputation and S15's persistence primitive; M3 `reveal` fetching missing ciphertexts via `get_data`.
- Q: CI jobs hosting the devnet E2E suites (S16 default, S17–S19 gated/scheduled); M4 release gate (Sepolia E2E, mainnet smoke seal, disk-loss restore drill) reusing S14/S19 capability; threat-model doc absorbing storage-side notes (journal-loss abandonment, wallet linkability of receipts).
