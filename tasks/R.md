### R1 — Define the verification report model and error taxonomy in `antseal-core::verify`
- Milestone: M0
- Size: M
- Deps: F: decoded bundle/manifest typed structs from the strict-canonical CBOR codec
- Spec: Reveal bundle — two proof layers; Verifier structural invariants (MVP-SPEC.md lines 116–121); Verification (lines 167–168)
- Do: Create the WASM-safe `VerificationReport` type: work metadata (work_id, title, format/app version, claimed time as an informational-only field, signature-scheme label slot), an evidence-layer result, a storage-linkage-layer result slot, per-anchor result slots (state + verified time + artifact metadata + fetch dates; absent-tolerant from day one), and the redaction/reveal-set data (per file: revealed spans, unrevealed unit spans, unrevealed-file placeholders). Define a `thiserror` `VerifyError` taxonomy with one distinct, field-identifying variant per failure class this domain owns (decrypt, padding, true-length, lengths, referential integrity, tiling, path-commit, partial-isolation, full-reveal material/cross-checks, raw-mirror binding), plus wrapper variants for C/G/F/A errors so every tamper row surfaces distinctly through `verify_bundle`. - Accept:

  - Every structural invariant in line 121 has a named, distinct error variant (unit-tested for distinctness, e.g. exhaustive-match test)
  - Report serializes deterministically (two serializations of the same report are byte-identical)
  - No secret material (`k_u`, salts, `W`) appears in any `Display`/`Debug` output of report or errors (test asserts redaction)
- Notes: Decide fail-fast vs collect-all error reporting (see Open decisions); design for both: typed first-error for the tamper matrix, optional multi-error collection for rendering.
  — **[2026-07-27] executed**: D27 resolved (hybrid, docs/decisions/D27-verify-error-mode.md); D29 recommended (byte-deterministic compact JSON, serde/serde_json exact-pinned; freeze reserved to Q14 via Q4/Q5 — docs/decisions/D29-report-byte-format.md). ### R2 — Implement per-unit evidence stages: decrypt, padding verify/strip, true-length binding, content-binding dispatch
- Milestone: M0
- Size: M
- Deps: R1; C: XChaCha20-Poly1305 open with AAD (C9); G: leaf-range verification against `fine_root` (G13); C: `unit_commit` recomputation (C6)
- Spec: Cryptography — unit encryption (line 91); Reveal bundle — evidence layer (lines 114, 118); Verifier structural invariants (line 121)
- Do: For each revealed unit entry: decrypt the embedded ciphertext with the bundled `k_u`, the nonce taken exclusively from the manifest unit table, and AAD = `seal_id ‖ LE64(unit_id)`; verify AEAD-plaintext length equals `padded_length = ⌈(true_length+1)/256⌉·256` recomputed from the manifest's `true_length` (rejects over-/under-padding); verify every byte beyond `true_length` is `0x00`; strip length-first to `true_length`; verify `true_length` equals the unit's manifest byte-range width. Then dispatch content binding by unit kind/coverage: fine-tree-covered units go through G's sub-cover → leaf → boundary-path verification against `fine_root`; non-covered units (`--no-fine-tree`, raw-mirror) recompute `unit_commit = SHA-256(0x02 ‖ unit_salt ‖ bytes)` via C and match the manifest.
- Accept:
  - Unit tests per stage with distinct errors: `UnitDecryptFailed`, `PaddedLengthMismatch`, `NonZeroPadding`, `TrueLengthRangeMismatch`, `FineRootBindingFailed` (wrapping G), `UnitCommitMismatch`
  - Edge vectors pass: empty unit (`true_length` 0 pads to 256), unit ending exactly on a 256-B boundary (one extra pad block), one-byte file (single-leaf tree)
  - Nonce is read only from the manifest unit table — a bundle-side nonce field neither exists nor is consulted (asserted against F's schema)
  - G's over-broad-cover rejection (node spanning an unrevealed real leaf) surfaces through this stage as a distinct wrapped error
  - WASM-safe (compiles for wasm32)

### R3 — Implement manifest/bundle structural checks: exact lengths, referential integrity, tiling invariant, path verification
- Milestone: M0
- Size: M
- Deps: R1; F: decoded types (coordinate whether fixed-length fields are enforced at decode or here); C: `path_commit` recomputation (C6)
- Spec: Verifier structural invariants (line 121); Salted commitments — per-file salts, raw mirror (lines 92, 95); Tamper matrix (line 168)
- Do: Implement, each as an explicit check with a distinct field-identifying error: (1) exact-length validation of every disclosed secret-adjacent byte string — `unit_salt`/`path_salt`/`file_salt` = 16 B; `s_root` and every GGM covering seed = 32 B; every boundary Merkle node hash = 32 B; (2) referential integrity — every bundle unit entry references an existing manifest `unit_id` with no duplicates, every touched-file/full-reveal entry references an existing `file_id`, covers/paths reference revealed units only; (3) the per-file tiling invariant over the manifest unit table (all files, regardless of reveal shape): non-mirror unit byte-ranges sorted, non-overlapping, exactly tiling `[0, size)`, with raw-mirror units exempted strictly by `kind` — and a raw-mirror wrongly participating in the tiling set is its own distinct error; (4) for every touched file, recompute `path_commit = SHA-256(0x05 ‖ path_salt ‖ path_utf8)` via C and match the manifest.
- Accept:
  - Distinct errors: per-field length variants, `UnknownUnitRef`, `DuplicateUnitReveal`, `UnknownFileRef`, `TilingViolation{unsorted|overlap|gap|out_of_bounds}`, `RawMirrorInTilingSet`, `PathCommitMismatch`
  - Tiling check runs on partial reveals too (manifest-level; unit test proves it fires without any revealed bytes)
  - Wrong-length mutation of each individual field class yields its distinct error — never a panic, never an undistinguishable generic decode error (coordinated with F if F's schema rejects first)
- Notes: If F encodes these as fixed-size CBOR byte strings, agree at M0 whose layer emits the length error; the tamper fixtures (R7) must pass either way with a field-identifying error.

### R4 — Implement reveal-shape classification and file-level checks: partial-reveal isolation, full-reveal cross-checks, raw-mirror binding
- Milestone: M0
- Size: L
- Deps: R2, R3; G: full fine-tree rebuild from `s_root` (G9); G: `canonicalize_v` pinned to the descriptor's recorded Unicode version (G2); C: `canon_commit`/`raw_commit` recomputation (C6)
- Spec: Verifier structural invariants (line 121); Raw mirror (line 92); Salted commitments (line 95); GGM fine tree (line 96); M0 milestone (line 153)
- Do: Classify each file's reveal shape: fully revealed iff every non-mirror `unit_id` of the file is in the bundle's revealed set; otherwise partial (or untouched). Enforce partial-reveal isolation: hard-reject any bundle containing `file_salt` or `s_root` for a partially revealed file (the leaf-exact GGM sub-cover of a covered per-unit reveal is explicitly permitted). For fully revealed files, require the full-reveal material (`file_salt`; `s_root` iff the descriptor records a fine tree) with a distinct error when absent, then: concatenate the verified non-mirror unit bytes in range order and match `canon_commit` (text) / `raw_commit` (binary) under `file_salt`; when a fine tree exists, rebuild the entire fine tree from the bundled `s_root` over those bytes via G and match `fine_root`. When the file's raw-mirror unit is also revealed: verify `raw_commit = SHA-256(0x03 ‖ file_salt ‖ raw_mirror_bytes)`, and enforce raw-mirror ↔ canonical binding — recompute `canonicalize_v(raw_mirror_bytes)` with the descriptor-recorded version via G and require byte-equality with the validated canonical bytes.
- Accept:
  - Distinct errors: `PartialRevealSaltLeak{file_salt|s_root}`, `FullRevealMaterialMissing{file_salt|s_root}`, `ConcatCommitMismatch{canon|raw}`, `FineRootRebuildMismatch`, `RawCommitMismatch`, `RawMirrorCanonicalizationMismatch`
  - `--no-fine-tree` full reveal runs only the concat→commit check (no tree rebuild); text-with-mirror full reveal runs all of: concat→`canon_commit`, tree rebuild→`fine_root`, mirror→`raw_commit`, `canonicalize_v(raw)==canonical`
  - Empty-file vector (no fine tree, one empty unit) verifies as a full reveal
  - Full-file reveal expressed via `--units` enumerating all non-mirror units classifies identically to `--all` for that file
- Notes: The "full reveal requires `file_salt`/`s_root` present" strictness is derived from line 121's mandatory cross-checks ("using the bundled `s_root`, the verifier MUST rebuild") — confirm as an M0 freeze decision (see Open decisions).

- Notes: **R59 is the same question one layer down, and the two should be taken together** — R59 owes R11's bundle-shaped adapter (a bundle's embedded ciphertexts + its encrypted-manifest record → `Vec<StorageRecord>`) through the public `StorageRecord::new` extension point, unbuilt for the identical cycle reason. The cli lib survives as a home on its own merits; the *"beside R21"* argument for it does not.

### R81 — `verify --live` cannot check the encrypted-manifest blob, so it is silent about the one blob the offline layer does check
- Milestone: M3
- Size: XS
- Deps: after U30 (the `--live` driver, and `collect_live`, which is where the absence is documented), R11 (`LiveSubject::EncryptedManifest`, `records_from_manifest`'s `encrypted_manifest` parameter, and the public `StorageRecord::new` extension point), R20 (the offline linkage layer — the only code in the tree that rebuilds the blob); D128 §3 R1 is the reason the two halves always render together (the offline half runs on **every** verify, so there is no configuration in which the asymmetry is hidden)
- Spec: Verifier — the storage layer and `--live` (MVP-SPEC.md line 119); the two proof layers rendered distinctly (line 116); Manifest storage record — anchored bytes ≠ stored bytes (line 98); core user flows — verify (line 38); M3 milestone (line 156)
- Discovered by: **the U30 lane** (2026-08-12), while building the bundle-shaped adapter that `StorageRecord::new`'s own docs name as M3's — by trying to add the manifest row and finding no public route to the bytes it would have to compare against.
- Problem: **one storage section, two halves, and they disagree about their own subject.** R11 defines `LiveSubject::EncryptedManifest` and `records_from_manifest` already takes an `encrypted_manifest: Option<(Address, &[u8])>` to build that row, so the live side's *shape* has always admitted it. What it cannot obtain is the **bytes**. The blob the sealer uploaded is `XChaCha20-Poly1305(k_m, nonce, MANIFEST_AAD, manifest_bytes)`, and reproducing it is exactly what R20's offline layer does — `check_storage_linkage`'s manifest arm calls `antseal_core::crypto::manifest_aead::recompute_manifest_blob`, which is **`pub(crate)`**. `encrypt_manifest` is public but draws a **fresh random nonce**, so it cannot reproduce the uploaded blob; `decrypt_manifest` runs the wrong direction. So the offline half checks the manifest and every unit, while `--live` checks every embedded **unit** ciphertext and nothing else — and the rendered section says which subjects it *found*, never which it could not *ask about*. A user reading a clean live section is being told less than the sentence sounds like. **The brief's framing — "the fix is a one-word visibility change" — is refused by the function's own rustdoc**, which argues the `pub(crate)` deliberately: *"The module docs' structural claim — no public API accepts a caller-supplied encryption nonce — is what keeps `(k_m, nonce)` single-use … A `pub` version of this function would be a general encrypt-under-a-chosen-nonce API wearing a verification name."* That is a nonce-reuse guardrail, not an oversight, and this row must not spend it by default. The countervailing measurement, which is why the arm is arguable rather than closed: `ManifestLinkageSubject`'s fields — `nonce`, `k_m`, `manifest_bytes`, `recorded_address` — are **already public**, because `check_storage_linkage` is a public stage, so the claim as written governs *functions that encrypt*, not the material itself.
- Do: **rule the route, then wire it — and the ruling is the expensive half.** The arms, one to be recorded with its reason at the code: **(a) widen `recompute_manifest_blob` to `pub`** — the cheapest edit and the one the discovery named, refused unless its own rustdoc's structural claim is rewritten in the same change, because leaving both standing ships a doc that its neighbour falsifies (the R79 shape, one crate over); **(b) mint a verification-shaped `pub fn` in `verify::storage_linkage`** taking the `ManifestLinkageSubject` the public stage already takes and returning the recomputed blob (or its `ContentAddress`), so the nonce arrives inside a named linkage subject rather than as a free parameter and the encrypt-door stays shut — still a widening, and still to be argued rather than assumed; **(c) compare addresses instead of bytes on the live path** — S15 fetches the blob and the recorded address is in hand, so an address comparison needs no plaintext-side recomputation at all, at the cost of changing `StorageRecord`'s shape, which currently requires a ciphertext copy to compare against (R11's, not this row's, so taking (c) makes this row R11-owning rather than XS); **(d) rule the absence permanent and render it** — cheapest of all and the only arm that is honest without any new API, but it must then *appear*: the live section states the subjects it could not reach, so the gap is a sentence a user reads rather than a comment in `collect_live`. **(d) is not exclusive with the others** and should ride whichever is taken, because a section that reports three of four subjects and says so is strictly better than one that reports three and stops. Whichever arm: the manifest row must be **reachable in a test that bends the manifest blob deliberately** and asserts the live section sees it — the offline layer's `StorageAddresses::RealExceptManifest` (R20's fixture handle) is the shape, driven through `MockBackend` rather than through hand-built inputs, which is R80's bridge and the reason these two are cheaper taken together.
- Accept:
  - `verify --live` over a work whose manifest blob was replaced on the network renders a **manifest** row in the live section, distinct from the unit rows, and the divergence is visible in the rendered output and in `--json` — or, under arm (d), the section states in R18-frozen wording that the encrypted manifest was not checked, and a test asserts that sentence is present on every `--live` run.
  - The chosen arm is recorded at the code with its reason, naming `recompute_manifest_blob`'s `pub(crate)` rustdoc and this row — a reader must not have to re-derive why the one-word change was or was not taken, and if it *was* taken, the rustdoc's structural claim is rewritten in the same change rather than left to contradict it.
  - The `collect_live` comment that records the absence is **deleted or rewritten in the same change**; a documented gap outliving its fix is the defect this row is made of, one layer up.
  - Zero format cost: no report field, no wire key, no new error code, `REPORT_VERSION` stays 1 and `ENVELOPE_VERSION` stays 1. `LiveSubject::EncryptedManifest` already exists and already serializes, so the live document gains a row it was always shaped for, not a key.
  - Exit codes untouched — D69 §3 R6 makes the live layer exit-code-free at the type level (R21 landed it as an absence; the live and linkage values are never parameters of `verdict_exit_rung`), and this row must not be the thing that reintroduces them.
- Notes: **the Q112 class** — shipped code that says less than its rendering implies — so it mints a row under protocol rule 8 rather than going to the ledger, and it changes what a user's `verify --live` reports. **XS in code, not XS in judgement**, exactly as R78 is: the sizing covers the wiring, and a lane that widens the visibility without answering the encrypt-door argument has not done the row. **Take it with R80.** R80 owes the `PersistenceReport → LiveInputs` bridge from a real `MockBackend`, which is the only place a bent manifest blob can be presented to the live path at all; a lane holding that fixture gets this row's test for free, and a lane doing this row without it is hand-building the inputs it was supposed to drive. The asymmetry is **recorded, not hidden**: `collect_live`'s comment states the bound in the lane's own words (*"`--live` proves persistence for every unit ciphertext the bundle embeds and says nothing about the encrypted manifest … the fix is one visibility change in a crate this lane may not write"*) — this row keeps that history and refuses only its last clause, on the rustdoc the lane could read but did not quote.

### R82 — The machine-interface snapshot cannot represent both feature builds, so the `ant-backend` machine surface is witnessed by nothing
- Milestone: M3
- Size: S
- Deps: after U30 (the third `Outcome` arm and the envelope's current shape — the last row to move `json-envelopes.txt`), U36 (the backend seam whose two `#[cfg]` arms are the divergence); U3 (the fixture registry and the rule that fixtures render through the **real** producer); U13 (the row the feature-ON sentence names as pending, and which has shipped); D65 (the tier partition that turns the envelope into a documented contract); Q153 (the ruling that keeps `heavy-features` local-only, which is why nothing remote can see this). Not an ordering dep: U69, which corrects a different fixture in the same file for a different reason — but the two touch the same committed snapshot and a lane taking one should read the other.
- Spec: CLI surface — `--json` machine-readable output (MVP-SPEC.md lines 147–149); core user flows — seal / restore / reveal (lines 34, 36, 40); M3 milestone (line 156)
- Discovered by: **the R22 lane** (2026-08-12), on a `--features ant-backend` run of the CLI suite; **attributed to HEAD by the wave owner** in the same act, by checking out HEAD's `backend.rs` and HEAD's snapshot and reproducing the failure there. This is the **Q112 class** — a product defect found *by* an instrument, minted immediately under rule 8: it governs what a user's `--json` run returns in the build that can actually reach the network.
- Problem: **one committed file, two machine surfaces.** `crates/antseal-cli/tests/snapshots/json-envelopes.txt` is a single snapshot, rendered through the real producers per U3's rule and compared byte-for-byte by `envelope_fixtures_match_the_committed_snapshot`. But `backend::unavailable` has **two `#[cfg]` arms with different text** — the feature-OFF arm says the build has no storage backend compiled in and names `--features ant-backend`; the feature-ON arm says the command is not yet wired to the backend it has. Three registered documents route through that function (`seal`, `restore`, and — since U28/U29 — `reveal`), so under `--features ant-backend` three lines of the snapshot differ from the committed bytes and the test fails. **A single file cannot document both builds**, so whichever one it documents, the other build's machine surface is pinned by nothing at all.
  **The red pre-dates wave 18, and that was measured rather than assumed**: HEAD's `backend.rs` already carries both arms and HEAD's `json-envelopes.txt` already holds the feature-OFF text, so the test was already failing under that feature before this wave began. Wave 18 made it **one line worse** — `reveal` became the third command through the seam — and did not create it.
  **It is invisible to CI by design, not by accident.** The only lane that builds this feature is `heavy-features`, which **Q153** ruled **local-only** (475 packages resolved against the default build's 120) and which is additionally diff-triggered, so a green 19-of-19 remote run is silent on it by construction. The defect can therefore sit through any number of green waves.
  Two things lift this above a ledger line. **(a) The feature-ON text is false.** It reads *"connecting it to this command's argument handling lands with **U13**"* — and U13 has shipped. `seal` is wired; `restore` and `reveal` are not, but they are not waiting on U13, so both messages send a user to an already-closed row. Three independent lanes have now reported that same sentence (U28, U29, R22), which is what makes it a standing defect rather than a stale comment. **(b) D65 has just made the envelope a documented contract with tiers** — the `command`, `ok`, `v`, `network` and `error.class`/`error.exit_code` keys are tier A and B, and the whole point of the registry is that a reviewed snapshot moves when they do. A second build whose machine surface drifts unwitnessed is a contract with no instrument.
- Do: **rule how a feature-varying machine interface is pinned, then fix the U13 sentence in the same act.** The arms, one to be recorded with its reason at the fixture registry: **(a) a second committed snapshot** (`json-envelopes.ant-backend.txt` or equivalent) selected by `#[cfg(feature = "ant-backend")]`, which keeps both texts and doubles the blessing surface — and must then answer who runs the second one, given Q153; **(b) a feature-parameterised fixture** — one file whose feature-varying documents are rendered per-arm and compared per-arm, so the committed bytes carry both texts and neither build is unwitnessed; **(c) make the message feature-invariant** — one sentence true of both builds, which deletes the divergence at its source, costs the feature-ON arm the specific thing it says, and is the only arm that leaves one snapshot correct everywhere. Whichever is taken, the **U13 sentence goes in the same change**: it must name what is actually pending for the command it refuses (`restore`'s and `reveal`'s own wiring), not a shipped row.
- Accept:
  - `cargo test -p antseal-cli --features ant-backend` runs `envelope_fixtures_match_the_committed_snapshot` **green**, and so does the default build — both asserted, because the defect is precisely that one of the two was never checked.
  - The chosen arm is recorded at `machine_mode.rs`'s fixture registry with its reason and a pointer to this row, so the next lane does not re-derive why one file is or is not enough.
  - **No `--json` envelope key moves**: `ENVELOPE_VERSION` stays 1, no key added, removed or renamed, and D65's tier A/B members are byte-unchanged in the default build's document set. Only the `error.message` string of the feature-ON arm is in scope, and it is tier C.
  - **The feature-ON refusal names no shipped row.** A test — not a review — pins that the message does not name `U13`, or names only rows that are open; a sentence pointing at closed work is the defect this row is half made of, and it has already recurred three times.
  - The fixtures are still rendered through the **real producer** (U3's rule, and the reason `unavailable` is `pub` at all) — no arm may be satisfied by hand-copying the second build's text into a file, which is the failure mode U19 and U3 both already paid for.
- Notes: **the divergence is deliberate and must not be deleted carelessly** — `unavailable`'s own rustdoc argues both arms in the strongest form (*"The two arms say different true things, which is the point: a message blaming the missing feature would be a lie in a build that has it"*), so arm (c) is a real option but is a **retraction of a recorded design choice** and has to be argued as one, not slipped in as a snapshot repair. **Take it with U69**: that row corrects a different `restore` entry in the same committed file for an unrelated reason (an envelope no build can emit), and two lanes blessing `json-envelopes.txt` from different premises will collide. **The row is S rather than XS because the ruling is the expensive half**, exactly as R79 and R81 are: the wiring is a file and a `#[cfg]`, and the question of who runs the second arm — given Q153's local-only ruling — is the part that outlives it.
